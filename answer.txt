0. 结论摘要
================================================================================

【最重要的发现】
shaolib_munitions 里的 `com.verr1.shaolib.munitions.projectile.dual_cannon`
这一整个包，本来就是为 cbcmoreshells 写的：

  - `NormalDualCannonProjectiles` 里的 7 个条目 ID 与 cbcms 现有的 7 种
    dual cannon 弹药一一对应（normal_ap_shot / normal_he_shell /
    normal_antiair_he_shell / normal_ap_shell / normal_apbc_shell /
    normal_sap_shell / normal_incendiary_he_shell）。
  - `DualCannonShellProperties.base(...)` 的 fallback 里，
    `cbc_projectile_effect_entity` 直接硬编码为
    `ResourceLocation("cbcmoreshells", <弹药 id>)`。
  - `MunitionsProjectiles` 里 **已经注册**了这 7 个 `ProjectileType`
    （NORMAL_AP_SHOT … NORMAL_INCENDIARY_HE_SHELL）。
  - `MunitionsProjectileClient` 里 **已经注册**了这 7 个客户端渲染行为，
    并且用 `cbcmoreshellsBlock("normal_ap_shell")` 之类去取 cbcms 的方块模型。

所以：**弹道 / 穿深 / 跳弹 / 爆炸 / 引信 / 客户端渲染这条主链路 shaolib 已经
全部实现好了，cbcms 需要做的是"拆掉自己的实体炮弹，改成在发射瞬间 spawn
shaolib 投射物"，而不是在 shaolib 之上再造一套。**

【但是不能无脑直接用 MunitionsProjectiles.NORMAL_* 】
因为 cbcms 有 4 件 shaolib 内置类型给不了的东西：

  a) 每发不同的 lifetime（炮管加成 + 指挥命令 + 装备修正）——shaolib 的
     `maxLifetimeTicks` 是类型级常量，`runtime.max_distance` 是配置级常量。
  b) extended_ap_shot / extended_antiair_he_shell 两种弹在 shaolib 里
     **没有**对应条目。
  c) 命中回调（`reduceCooldownOnHit` → 缩短快速填装冷却 + 提示音）。
     —— 这一条 shaolib 已留了口子：`DualCannonShellState.setHitCallback()`。
  d) cbcms 自己的曳光 / 尾迹 / 水花网络包（ClientboundCBCMSTrailPacket /
     ClientboundCBCMSSplashPacket）。

因此最终方案是 **路线 B**：cbcms 自建一套 `ProjectileType`（复用 shaolib 的
State/Behavior/Serializer 作为父类，自己写子类），把 shaolib 内置的 7 个
NORMAL_* 只当作"参考实现 + fallback 数值来源"，不直接 spawn 它们。

【交付形态】
迁移完成后：
  - 9 个 `*Projectile` 实体类全部删除，`CBCMSEntityTypes` 里 9 条
    `dualCannonProjectile(...)` 注册全部删除。
  - 方块（NormalAPShellBlock 等）、方块物品、方块实体、模型、贴图、
    ponder、配方 **全部保留不动**——它们仍然是"装填进炮膛的弹药方块"，
    并且 shaolib 客户端行为要靠这些方块的模型来渲染飞行中的炮弹。
  - `MountedDualCannonContraption.fireShot` 里 `level.addFreshEntity(projectile)`
    改成 `ShaolibProjectiles.spawn(...)`。
  - **不注册任何新物品**，引信通过映射到 shaolib_munitions 已注册的
    3 个引信物品（impact_delay_fuze / body_only_proximity_fuze / timed_fuze）
    的 ItemStack 来实现。

【移植后消解的两个约束（上一版文档记的「偏离」现已作废）】
  a) 上一版说「不能有自己的 State 子类」——那是因为
     shaolib 的 DualCannonShellBehavior 把状态类型写死成 DualCannonShellState。
     现在 behavior 由 cbcms 自己持有，签名是
     `DualCannonBehavior<P> extends AbstractFuzedShellBehavior<DualCannonState, P>`，
     而父类的 S **是类型变量**，所以 DualCannonState 可以正常存在。
     → lifetime / 尾迹锚点等已从 schema 移回 State（更干净，
       只有动态属性 JSON 必须留在 schema，因为 encodedJson 解析器
       只能通过 ProjectileDataAccessor 读取）。
  b) 上一版说「Serializer 是 final 不能继承」——现在 DualCannonSerializer
     是 cbcms 自己的类，正常继承 FuzedShellSerializer 即可。

【CBCMSLegacyPenetration —— 保留的备选击穿算法】
  来源：AbstractDualCannonProjectile.getHitNearbyAverageToughness(...)
        + NormalSAPShellProjectile 里 `if (this.alternativePenetration())` 分支
        （alternativePenetration() 恒返回 false，所以那段是死代码）。
  与在用模型的区别：
    在用（DualCannonPenetrationModel）：动量制。
        mass × velocity × bonus × incidence  vs  被击中那一格的 toughness，
        中间有概率带。对入射角/速度敏感，薄板与厚板拦阻能力接近。
    备选（CBCMSLegacyPenetration）：装甲厚度制。
        对命中面背后 3×3×3 深共 27 格取平均 toughness，
        对比纯质量导出的 mass²×0.4 + mass×1.2 − 1.5。
        不看速度与入射角，因此奖励间隔/复合装甲，口径成为主导变量，
        更接近真实穿深表的行为。
  当前未接线。接线点在 DualCannonBehavior.tickServer —— 它把
  DualCannonPenetrationModel::resolve 作为 block impact resolver 传给
  MunitionImpactSweep.sweep(...)，换成一个调用 CBCMSLegacyPenetration.penetrates
  的 resolver 即可（移植之后这个类归 cbcms 所有，改起来是一行）。
  注意 resolver 必须返回完整的 MunitionImpactOutcome：
  耐久质量扣减、跳弹处理、stop/spall 特效都在 resolver 内部，
  替换实现要把这些一并覆盖，而不只是回答「穿不穿」。

【阶段二的三个取值决定（与第 5 节原文不同，此处为准）】

  1) runtime.max_distance 一律写 5000，而不是「按 lifetime 换算」。
     原因：旧实现**根本没有距离上限**，只有 tick 寿命。
     真正的限制器是 DualCannonBehavior.expireOnLifetime，
     max_distance 只作为跑飞兜底。若照 5.5 表里写成 180（shaolib fallback 值），
     初速 8 × 寿命 40 tick ≈ 320 格的弹会被腰斩。

  2) effects.cbc_projectile_effect_entity 指向 **CBC 的实体**
     （createbigcannons:ap_shell / createbigcannons:he_shell），
     而不是 cbcmoreshells 自己的实体。
     原因：这个字段被 CbcMunitionEffects 用
     `BuiltInRegistries.ENTITY_TYPE.getOptional(...)` 解析（找不到会静默回退到
     CBC 的 AP_SHELL）。阶段六删掉 cbcms 的 9 个实体后，
     指向 cbcmoreshells:* 就会变成悬空引用并静默降级；
     现在直接指向 CBC 的稳定实体，跨阶段六不受影响。
     注意这与客户端渲染无关 —— 渲染用的方块 id 是单独传给
     DualCannonShellClientBehavior 的（见 Entry.renderedBlock）。

  3) 旧的 data/cbcmoreshells/munition_properties/projectiles/*.json **暂不删除**，
     因为旧的 9 个实体炮弹还在用它们。阶段六一并清理。

【§6.5 的顺序问题已经查明，不需要再实测】
  ServerProjectileRuntime.spawn 的实际顺序（反编译确认）：
    60: initializer.initializeInstance(projectile)
    61: state = type.createServerState(...)
    63: initializer.initializeHandle(entry)     ← handle 阶段
    64: type.onSpawn(level, projectile, state)  ← onSpawn 在其后
  → **initializeHandle 在 onSpawn 之前**。
    所以 6.5 写的方案成立：在 handle 阶段 installFuze，
    随后 onSpawn 里的 MunitionFuzes.onInstalled 能看到并初始化这枚引信。
  → 同理也说明：在 handle 阶段直接 setDurabilityMass 不会被 onSpawn 的
    initializeDurabilityMass 覆盖（后者只在未设值时写入）。
    但阶段二仍然选择走 DYNAMIC_PROPERTIES，因为
    DualCannonPenetrationModel.resolve 里也会调
    initializeDurabilityMass(ballistics.durabilityMass() * durabilityModifier)，
    只有把值放进属性里，两条路径才一致。

【三处 CBC → shaolib 的行为落差（已在代码 javadoc 中写明）】
  1) **哑弹机制丢失**：CBC 的 Impact / Inertia 引信有 FUZE_DAMAGE 耐久
     与 getDetonateChance() 的概率失效，shaolib 的对应引信必定起爆。
     迁移后这两种引信比原来更可靠。
  2) **近炸引信的探测对象改变**：CBC 的 ProximityFuzeItem 扫描的是**实体**
     （level().getEntities(...)），而 shaolib 只有 BodyOnlyProximityFuzeItem，
     扫描的是**物理刚体**（船体等）。
     → 迁移后近炸弹会在靠近船体时引爆，但**不会**在靠近飞机/生物时引爆。
     这对防空弹影响最大。彻底解决需要 shaolib 侧提供实体近炸引信；
     目前没有，而 cbcms 不注册物品就无法自己补一个。
  3) **有线引信失去触发源**：WiredFuzeItem 靠发射点的红石信号触发，
     炮弹出膛后红石够不着，退化为触发引信。

3. 架构决策（为什么这么切）
================================================================================

3.1 两条候选路线

  路线 A：直接 spawn shaolib 内置的 MunitionsProjectiles.NORMAL_*
    优点：零注册、零客户端工作，最快。
    缺点：
      - 每发 lifetime / spread / 耐久质量修正只能靠 state 上现成的
        durabilityModifier 那一个字段，lifetime 完全无法按发改。
      - extended_ap_shot / extended_antiair_he_shell 无落点。
      - 客户端行为已被 shaolib 注册死，cbcms 的尾迹/水花包插不进去。
    → 适合做"第一步冒烟验证"，不适合最终形态。

  路线 B（推荐，本文按此展开）：cbcms 注册自己的 ProjectileType
    - 新建 `CBCMSDualCannonProjectiles`，为 9 种弹各注册一个
      `ProjectileType<CBCMSDualCannonShellState>`，id 用
      `cbcmoreshells:normal_ap_shell` 等（与方块同名，方便查表）。
    - State 继承 `DualCannonShellState`，加 cbcms 自己的字段。
    - Behavior 继承 `DualCannonShellBehavior<P>`，覆写 tick 加 lifetime 判定
      与尾迹包发送。
    - Serializer 继承 `DualCannonShellSerializer<S>`。
    - Schema 用 `FuzedShellData.SCHEMA.extend()` 加 cbcms 自己的字段。
    - 客户端用 `ClientProjectileBehaviors.register(type, new DualCannonShellClientBehavior<>(...))`
      —— 直接复用 shaolib 的客户端行为类即可（它已经会渲染 cbcms 方块模型）。
    优点：全部 4 个缺口都能补上，且仍然复用 shaolib 的弹道/穿深/引信主体。

3.2 "不复用代码，自己重写"的边界说明
    这里的"自己重写"指：**cbcms 侧不保留任何旧的实体炮弹实现，全部按
    shaolib 的 State/Behavior/Serializer 三件套范式重新写一遍**；
    而不是指要把 shaolib 的 DualCannonShellBehavior / PenetrationModel /
    MunitionFuzes 再抄一份到 cbcms —— 那些是库，继承/调用即可。
    判断标准：cbcms 里不应再出现 `extends AbstractCannonProjectile`、
    `EntityDataAccessor`、`calculateBlockPenetration` 这类 CBC 实体炮弹的痕迹。

3.3 弹种 → Kind 映射表（Kind 决定爆炸威力公式与命中分支）

    cbcms 弹药                     shaolib Kind      属性类型
    ---------------------------------------------------------------------
    normal_ap_shot                 AP_SHOT           DualCannonShellProperties
    extended_ap_shot               AP_SHOT           DualCannonShellProperties
    normal_he_shell                HE                DualCannonShellProperties
    normal_antiair_he_shell        ANTIAIR_HE        DualCannonShellProperties
    extended_antiair_he_shell      ANTIAIR_HE        DualCannonShellProperties
    normal_ap_shell                APHE              DualCannonShellProperties
    normal_apbc_shell              APBC              DualCannonShellProperties
    normal_sap_shell               SAP               DualCannonShellProperties
    normal_incendiary_he_shell     INCENDIARY        DualCannonIncendiaryShellProperties

    注：extended_* 两种在 shaolib 没有 MunitionPropertyType，
        必须由 cbcms 调用
        `DualCannonShellProperties.createType(cbcms.id("extended_ap_shot"), fallbackSupplier)`
        自行注册（这是注册"属性类型"，不是注册物品，不违反"不注册任何物品"）。

4.2 State：CBCMSDualCannonShellState extends DualCannonShellState

  父类已提供：durabilityModifier / launchY / hitCallback /
              travelled / durabilityMass / penetrations / ricochets /
              terminalAge / detonationVelocity / fuzeStack …
  cbcms 需要新增（都是 transient 或需序列化的服务端状态）：

    - int lifetimeTicks           本发的最大存活 tick（含炮管/指挥/装备修正）
    - float maximumMomentum 覆盖  （若不想走 JSON 覆盖，可放这里）
    - 尾迹发包用的 traced / sendTrail / xOldT,yOldT,zOldT
      （从旧 AbstractDualCannonProjectile 的 tick() 里搬过来的逻辑，
        但注意：**重写而不是复制**，用 ProjectileServerContext 取位置）
    - boolean hitTargetOnce       对应旧的 hitTarget 去重标记
      （也可以直接放在 hitCallback 的闭包里，见 7.5）

  序列化：CBCMSDualCannonShellSerializer 覆写 saveAdditional/loadAdditional，
  先 `super.` 再写 cbcms 自己的键（LifetimeTicks / Traced / TrailAnchor 等）。

4.3 Behavior：CBCMSDualCannonShellBehavior<P> extends DualCannonShellBehavior<P>

  构造：`super(propertyResolver, kind)`（父类有接收 resolver 的构造器）。

  需要覆写的钩子（只覆写这几个，其余全部继承）：

  (a) onSpawn(context)
      - `super.onSpawn(context)`  ← 会 initializeDurabilityMass + 装引信
      - 记录尾迹锚点（xOldT/yOldT/zOldT = projectile.position()）
      - 若 lifetimeTicks 未被外部设定，回落到属性里的默认值

  (b) tickServer(context)
      - **先做寿命判定**：
        `if (projectile.ageTicks() >= state.lifetimeTicks())
             context.runtime().discard("cbcms_lifetime"); return;`
        —— 这是旧 `age > maxAge → discard()` 的等价物。
      - **再做尾迹/水花发包**（旧 tick() 里 sendTrail 那段的重写版）：
        用 `context.level()` 与 `projectile.position()`，判定
        `projectile.isEmbedded()` / 水中（`level.getFluidState(blockPos)`）。
        发 `ClientboundCBCMSTrailPacket` / `ClientboundCBCMSSplashPacket`。
      - 最后 `super.tickServer(context)` 走 shaolib 的完整流水线。
      注意：父类 tickServer 内部已经处理 embedded/armed/terminal 分支，
            所以 cbcms 的寿命判定要放在 super 之前，且对 terminal 状态
            应当放行（terminal 有自己的 terminalTtlTicks）。

  (c) applyImpactOutcome(context, outcome)  —— 可选
      父类已经会调 `state.hitCallback().onHit(context, outcome)`，
      所以"命中缩短冷却"**不需要**覆写这里，用 hitCallback 即可（见 7.5）。
      只有当 cbcms 想改动 AP_SHOT/SAP 之外的命中语义时才覆写。

  (d) detonatePayload(context, properties, position, velocity)  —— 可选
      父类已实现 CBC 风格爆炸 + INCENDIARY 分支（走 IncendiaryEffectService）。
      cbcms 只需实现 IncendiaryEffectService 并注入 Holder（见 4.6），
      **不要**在这里重写纵火逻辑。

  (e) explosionPowerMultiplier(context) —— 若 cbcms 想保留自己那套
      `(durabilityModifier-1)/1.2+1` 的系数，父类的公式已经与旧实现一致
      （逐条比对过：HE/INCENDIARY = (m-1)/1.2+1，ANTIAIR = (m-1)/1.5+1 × 高度倍率，
        APHE = m*0.47+0.4，APBC = m*0.45+0.4，SAP = m*0.82+0.18，AP_SHOT = 0）。
      所以**不需要覆写**。这是 shaolib 侧照着 cbcms 旧实现写的。

4.4 Schema：CBCMSDualCannonData

    private static final ProjectileDataSchema.Builder B = FuzedShellData.SCHEMA.extend();
    LIFETIME_TICKS  : INT,    default 30, SPAWN_ONLY
    DYNAMIC_PROPS   : STRING, default "", SPAWN_ONLY   （见 5.4）
    // TRACER 用父 schema 里现成的 FuzedShellData.TRACER
    public static final ProjectileDataSchema SCHEMA = B.build();

  说明：`lifetime` 放 schema 而不是只放 State，是因为客户端也可能想知道
  （比如曳光淡出）；如果客户端不需要，放 State + Serializer 更省带宽。
  推荐：**lifetime 放 State（不同步），DYNAMIC_PROPS 放 schema（SPAWN_ONLY）**。

4.5 类型注册：CBCMSDualCannonProjectiles

  每个弹种一条，形如：

    public static final ProjectileType<CBCMSDualCannonShellState> NORMAL_AP_SHELL =
        ShaolibProjectiles.register(
            ProjectileType.builder(Cbcmoreshells.id("normal_ap_shell"),
                                   (proj, level) -> new CBCMSDualCannonShellState())
                .schema(CBCMSDualCannonData.SCHEMA)
                .motionModel(MunitionMotionModels.configured(resolver))
                .orientationSync(ProjectileOrientationSync.NONE)
                .behavior(new CBCMSDualCannonShellBehavior<>(resolver, Kind.APHE))
                .serializer(new CBCMSDualCannonShellSerializer<>())
                .syncIntervalTicks(10)
                .maxLifetimeTicks(240)      // 硬上限，取足够大
                .build());

  其中 resolver =
    `MunitionPropertyResolver.encodedJson(propertyType, CBCMSDualCannonData.DYNAMIC_PROPS)`
  （若某弹种不需要按发覆盖，用 `MunitionPropertyResolver.configured(propertyType)`）。

  注意 maxLifetimeTicks 的语义：这是 shaolib 的**硬性兜底**，
  cbcms 的按发 lifetime 由 4.3(b) 的判定负责，所以这里应取
  `所有可能 lifetime 的上界 + 余量`（例如 600），避免炮管加成后被硬上限截断。

  类加载触发：写一个空的 `public static void register() {}`，
  在 `Cbcmoreshells` 构造器里调用一次，保证静态字段被初始化。

4.6 纵火服务注入

  在 mod 初始化（服务端侧即可）调用：

    IncendiaryEffectService.Holder.set((level, position, fireChance, fireRange) -> {
        // 把旧 NormalIncendiaryHEShellProjectile.spawnFire(...) 的逻辑重写在这里
        // 含 CBCMSCompatTransformers.spawnFireOnSublevel(...) 那段
    });

  注意：`Holder.set` 是全局单例，若同一整合包里 Taovmod 之类也 set，
  会互相覆盖。建议在 set 之前先 `get()` 保存旧值并在自己实现末尾链式调用，
  或者在文档里注明冲突风险。

4.7 需要删除的旧逻辑（不要迁移）

  - `AbstractDualCannonProjectile.calculateBlockPenetration(...)`
    → 由 `DualCannonPenetrationModel.resolve` + `DualCannonImpactProperties`

        penetrationMassPenaltyScale / bounceMassPenaltyScale）取代。
  - `getHitNearbyAverageToughness(...)` / `alternativePenetration()`
    —— **不要删**。这两个是以前的技术储备（面积采样式击穿模型），
       已在阶段一移植为 `CBCMSLegacyPenetration`，见 0.5 节。
       删除旧实体类时确认该文件已存在即可。
  - `onTickRotate()` / `lerpRotation` —— shaolib 用 orientation 四元数。
  - `ignoreExplosion` / `getForces` / `getDragForce` 等 CBC 实体钩子。
  - `FuzedDualCannonProjectile` 整个类（引信逻辑全部移交 MunitionFuzes）。

    （addedChargePower / minimumChargePower / canSquib / addedRecoil /
      initialVelocity / projectileSpread / minimumSpread /
      reloadTimeCoefficient / cooldownReductionRate）
    —— 9 个字段里已经覆盖了 cbcms 12 个字段中的 9 个。
    缺 3 个：`lifetime`、`smashToughness`、`maximumMomentum`。
    其中 smashToughness / maximumMomentum 在
    `DualCannonImpactProperties` 里已有（smashToughness / maximumMomentum），
    所以 **实际只缺 `lifetime` 一个**。
    → `lifetime` 用 `runtime.terminal_ttl_ticks` 之外的方式表达，或
      放进 cbcms 自己的一张表（见做法 2）。

  做法 2（推荐）：cbcms 保留一个精简的 `CBCMSDualCannonLaunchProfile` record，
    只放 shaolib 表达不了的：`int lifetimeTicks`，
    其余全部从 `MunitionConfigManager.properties(type).dualCannon()` /
    `.dualImpact()` 读。
    这样数据只有一份来源（shaolib JSON），不会两边漂移。

5.3 方块 ↔ 弹药 的查表：CBCMSDualCannonMunitionRegistry

  这是整个迁移的枢纽。旧代码之所以到处 `getProjectile(level, stack)`，
  就是因为没有这张表。新建：

    record Entry(
        ProjectileType<CBCMSDualCannonShellState> type,
        MunitionPropertyType<? extends DualCannonMunitionProperties> propertyType,
        DualCannonShellBehavior.Kind kind,
        int defaultLifetimeTicks,
        boolean fuzed,
        boolean baseFuze              // 旧 BigCannonFuzePropertiesComponent.baseFuze()
    )

    static final Map<Block, Entry> BY_BLOCK;      // NormalAPShellBlock → …
    static Entry of(Block block);
    static Entry of(BlockState state);
    static Entry of(ItemStack stack);             // BlockItem → Block
    static DualCannonMunitionProperties props(Entry e);  // 走 MunitionConfigManager

  用途：
    - fireShot 里判定弹种、取 type、取发射参数（不再 new 实体）
    - DualCannonMountPoint 取 reloadTimeCoefficient
    - CBCMSTooltip 取属性生成 tooltip

  填表时机：静态初始化即可（Block 对象在 CBCMSBlocks 里已是 DeferredHolder，
  用 `CBCMSBlocks.NORMAL_AP_SHELL_BLOCK.get()` 需延迟到注册完成后；
  建议做成 lazy init 或在 `FMLCommonSetupEvent` 里 build）。

5.4 每发动态覆盖：DYNAMIC_PROPS

  在 fireShot 里，把本发的修正编码成 JSON 字符串写进 schema：

    {
      "overrides": {
        "ballistics": { "durability_mass": <durabilityMassModifier * base> },
        "runtime":    { "max_distance":    <按本发 lifetime 换算> }
      }
    }

  `MunitionPropertyResolver.encodedJson(...)` 会自动：
    - 空串 → 直接用 MunitionConfigManager 的配置
    - 有 "template" → 以该模板为 fallback
    - 用 "overrides"（或整个 root）做逐字段覆盖
    - 解析失败 → 静默回落到配置
  并且它内部有 WeakHashMap 缓存，每个 ProjectileInstance 只解析一次。

  注意：`durabilityModifier` 本身有 `DualCannonShellState.setDurabilityModifier()`
  这个专门字段（爆炸威力倍率公式要用它），所以：
    - **爆炸威力倍率** → `state.setDurabilityModifier(durabilityMassModifier)`
    - **实际耐久质量** → `state.setDurabilityMass(durabilityMassModifier * base)`
      （在 handle initializer 里 set，会覆盖 onSpawn 里的
        initializeDurabilityMass，因为后者只在未设值时生效 —— 注意顺序：
        `initializeDurabilityMass` 只在 `hasDurabilityMass()==false` 时写入，
        而 spawn initializer 的 handle 阶段在 onSpawn 之前还是之后，
        需实测确认；稳妥做法是走 DYNAMIC_PROPS 的
        `ballistics.durability_mass`，让 onSpawn 自己读到正确值。）
    ↑ **这一条是实施时最容易出错的地方，务必实测验证。**

6. 阶段三：引信重定向（不注册任何物品）
================================================================================

6.1 问题本质

  `MunitionFuzes.active(stack)` 的判定是
  `stack.getItem() instanceof MunitionFuzeItem`。
  CBC 的 `FuzeItem` 不实现这个接口，所以 **CBC 引信物品无法直接塞进
  shaolib 的 FuzedMunitionState**。

  又因为要求"不注册任何物品"，cbcms 不能自己注册一个实现
  `MunitionFuzeItem` 的桥接物品。

  → 唯一正解：**发射瞬间做一次"引信翻译"**，把玩家插在弹药方块里的
    CBC 引信 ItemStack，翻译成一个 shaolib_munitions 已注册引信物品的
    ItemStack（带上对应的 CustomData），再 `installFuze` 进 state。
    这个翻译出来的 ItemStack 只存在于投射物状态里，**永远不会掉落成物品实体**，
    所以不构成"注册物品"。

6.2 映射表：CBCMSDualCannonFuzeMapper

  输入：`ItemStack source`（从弹药方块的 CBCDataComponents.FUZE 读出）
  输出：`MappedFuze(ItemStack stack, boolean initiallyTriggered, int countdownTicks)`

  规则：

    source 为空
        → MappedFuze.EMPTY（无引信弹，走 shaolib 的"无引信 → 尝试嵌入"分支）

    source.getItem() instanceof MunitionFuzeItem
        → 原样透传 `source.copy()`（别人已经塞了 shaolib 引信）

    rbasamoyai.createbigcannons.munitions.fuzes.TimedFuzeItem
        → MunitionsItems.TIMED_FUZE
          TimedFuzeItem.setTimeTicks(mapped,
              source.getOrDefault(CBCDataComponents.FUZE_TIMER, 20))

    DelayedImpactFuzeItem  /  DelayedInertiaFuzeItem
        → MunitionsItems.IMPACT_DELAY_FUZE
          ImpactDelayFuzeItem.setDelayTicks(mapped,
              source.getOrDefault(CBCDataComponents.FUZE_TIMER, 20))

    ImpactFuzeItem  /  InertiaFuzeItem
        → MunitionsItems.IMPACT_DELAY_FUZE
          ImpactDelayFuzeItem.setDelayTicks(mapped, 0)     // 触发即引爆

    ProximityFuzeItem
        → MunitionsItems.BODY_ONLY_PROXIMITY_FUZE
          BodyOnlyProximityFuzeItem.setRadius(mapped,
              max(1.0, source.getOrDefault(CBCDataComponents.DETONATION_DISTANCE, 1)))
          BodyOnlyProximityFuzeItem.setArmingDistance(mapped, 0.0)
          （若想保留 CBC 的"出膛一段距离后才解保险"，把 armingDistance
            设成炮口安全距离，例如 8.0；armingTicks 默认 5 tick）

    WiredFuzeItem
        → 无直接对应。三种处理任选：
          a) 映射成 TIMED_FUZE + 一个极大 TimeTicks（近似"不自爆"）
          b) 映射成 IMPACT_DELAY_FUZE(0)（近似触发引信）
          c) MappedFuze.EMPTY（等同无引信）
          建议 (b)，并在 tooltip 里注明该引信在双联装炮上退化为触发引信。

    其他未知 FuzeItem
        → MappedFuze.EMPTY，并 LOGGER.debug 一条，方便排查。

6.3 base_fuze（弹底引信）语义的处理

  旧 cbcms：`BigCannonFuzePropertiesComponent.baseFuze()` 只影响两件事：
    (1) `FuzedDualCannonProjectileBlock` 里引信插孔在哪个面（视觉/交互）
    (2) `FuzeItem.onProjectileClip(..., baseFuze)` / `onProjectileImpact(..., baseFuze)`
        传给 CBC 引信，让弹底引信"穿透后才起爆"

  迁移后：
    (1) **完全保留**在方块层（`isBaseFuze()`），不受影响。
    (2) shaolib 侧没有 baseFuze 概念，但 `DualCannonShellBehavior`
        对 `Kind.isApheLike()`（APHE / APBC）已经内置了
        "PENETRATE 之后才调 MunitionFuzes.onImpact" 的行为
        —— 这正是弹底引信的效果。
        所以：**base_fuze=true 的弹种，其 Kind 应落在 APHE / APBC**；
        若有 base_fuze=true 但 Kind 不是 APHE-like 的弹，
        需要在 CBCMSDualCannonShellBehavior 里覆写 `applyImpactOutcome`
        把该判定扩展到自己的 Kind。
        实施前先跑一遍 9 个 JSON 的 base_fuze 值，列出例外。

6.4 引信在方块层的读取（不变）

  `FuzedDualCannonProjectileBlock.getFuzeFromBlocks(blocks, registries)`
  从 `info.nbt().getCompound("components").get("createbigcannons:fuze")`
  解析出 ItemContainerContents → ItemStack。
  **这段逻辑保留不动**，只是它的返回值不再喂给实体，而是喂给 FuzeMapper。

  同理 `getTracerFromBlocks(...)` 保留，返回值用于设
  `projectile.set(FuzedShellData.TRACER, true)`。

6.5 安装时机

  在 `ShaolibProjectiles.spawn(...)` 的 `ProjectileSpawnInitializer.both(...)`
  的 **handle 阶段**做：

    handle -> {
        MappedFuze mf = CBCMSDualCannonFuzeMapper.map(cbcFuzeStack);
        if (!mf.stack().isEmpty()) {
            handle.state().installFuze(mf.stack());
            mf.applyInitialState(handle.state());   // 若需预触发
        }
    }

  `installFuze` 会重置 fuzeAgeTicks/countdown/triggered；
  随后 `onSpawn` 里 `MunitionFuzes.onInstalled(context)` 会调
  引信物品的 `onInstalled`。
  ⚠ 顺序依赖：`spawn` 内部是先 initializeInstance → 建 state →
  initializeHandle → onSpawn，还是别的顺序，实施时用日志实测一次；
  若 handle 阶段在 onSpawn 之后，则 `onInstalled` 不会被调用到新引信，
  需要改在 instance 阶段用 DYNAMIC_PROPS 传引信、或在 Behavior.onSpawn
  里自己 install。**这是第二个必须实测的点。**

7.5 命中回调（替代 reduceCooldownOnHit）

  旧逻辑在 `AbstractDualCannonProjectile.reduceCooldownOnHit(BlockPos)`：
    - 只触发一次（hitTarget 标记）
    - `hitShip(pos)`：|x|>1e7 || |z|>1e7 才算命中船（VS2 的子世界坐标特征）
    - 若 `CBCMSConfigs.server().notifyOnHit`，在 contraption 世界坐标附近
      给玩家播 ANVIL_LAND
    - `contraption.reduceCooldown(getCooldownReductionRate())`

  新做法：在 fireShot 里构造一个 `DualCannonHitCallback` 闭包塞进 state：

    final MountedDualCannonContraption self = this;
    final float rate = (float) props.dualCannon().cooldownReductionRate();
    final boolean[] done = { false };
    DualCannonHitCallback cb = (ctx, outcome) -> {
        if (done[0]) return;
        BlockPos hitPos = outcome.hit().getBlockPos();   // 名称以实际 API 为准
        if (!isShipHit(hitPos)) return;
        // 通知音 + self.reduceCooldown(rate)
        done[0] = true;
    };

  ⚠ 注意：`hitCallback` 在 `DualCannonShellState` 里是 **transient**，
    不会被序列化。也就是说**服务器重启 / 投射物存盘后，回调会丢失**。
    旧实现的 `contraption` 字段也是同样的非持久引用，所以行为等价，
    但要在代码里注释清楚这一点。

  ⚠ `hitShip(pos)` 那个 |坐标|>1e7 的 hack 依赖 VS2 子世界坐标。
    shaolib 有 `SourceBodyMarkedProjectileState` / body 查询体系，
    若整合包里有 Synaxis/VS，建议改用
    `outcome.hit()` 携带的 body 信息判定，比坐标 hack 可靠。
    若不引入新依赖，就照搬旧判定（但要注释"这是坐标 hack"）。

12. 风险、坑与注意事项
================================================================================

12.1 【必须实测】spawn initializer 的执行顺序
  `ProjectileSpawnInitializer.both(instanceInit, handleInit)` 里，
  handleInit 与 `Behavior.onSpawn` 谁先执行，决定了：
    - `installFuze` 是否会被 `onSpawn` 里的 `MunitionFuzes.onInstalled` 看到
    - `setDurabilityMass` 是否会被 `initializeDurabilityMass` 覆盖
  若顺序不利，改用 DYNAMIC_PROPS 传值 + 在自己的 Behavior.onSpawn 里
  读取并 install。

12.2 【坐标系】contraption 局部坐标 vs 世界坐标
  这是最容易踩的坑。旧代码 `projectile.setPos(spawnPos)` 传的是
  `entity.toGlobalVector(...)` 的结果，在有 VS2 子世界时仍是子世界坐标。
  shaolib 的 spawn 要真世界坐标，必须过
  `CBCCompatTransformers.transformVec3(level, pos, entity.position())`
  和 `transformLocationNormal(level, entity.blockPosition(), dir)`。
  参考实现：Taovmod2 `CbcMountedCannonShaolibReplacement.worldKinematics(...)`。

12.3 【lifetime 语义】tick 寿命 → shaolib 没有等价物
  三种表达方式，按需选：
    (a) 自己在 Behavior.tickServer 里判 ageTicks（本文推荐）
    (b) 换算成 runtime.max_distance ≈ lifetimeTicks × 平均速度
        （不准，因为有重力与阻力）
    (c) 提高 type 的 maxLifetimeTicks 到统一上限，不做按发区分
        （放弃炮管/指挥/装备的寿命加成）
  推荐 (a)，并把 type 的 maxLifetimeTicks 设为所有可能值的上界 + 余量。

12.4 【IncendiaryEffectService 是全局单例】
  `Holder.set()` 会覆盖别人的实现。若整合包同时装了 Taovmod 或其他
  也用 shaolib 的模组，会互相踩。建议链式包装（保留旧值并调用）。

12.5 【MunitionPropertyTypes 重复 id 会抛异常】
  `register` 对重复 id 抛 `IllegalStateException`。
  cbcms 的 9 个必须用 `cbcmoreshells` 命名空间。
  且类加载顺序要保证 —— 静态字段初始化在同一个类里，
  用 `register()` 空方法触发。

12.6 【hitCallback / contraption 引用不持久】
  投射物存盘再读回后 hitCallback 会变回 NOOP。
  旧实现的 contraption 字段也一样。行为等价，但要写注释。

12.7 【extended_* 两种弹的平衡】
  它们在 shaolib 里没有基线数值。实施时先用对应 normal_* 的 fallback
  做基线，再按旧 JSON（extended_ap_shot.json /
  extended_antiair_he_shell.json）的数值调回去。

12.8 【addedChargePower 的旧 bug】
  MountedDualCannonContraption:443 对 secondary 也用 primary 的
  addedChargePower。迁移时要么修正、要么显式保留并注释，
  不要在不知情的情况下改变数值行为。

12.9 【DualCannonProjectileBlock.getProjectile 的删除影响】
  这两个抽象方法在 9 个 Block 里都有实现。删掉抽象声明后，
  9 个实现也要删。若某处 API 兼容性有要求，可保留方法但改为
  `throw new UnsupportedOperationException("migrated to shaolib")`
  —— 不推荐，直接删干净。

12.10 【数据包路径】
  `SimpleJsonResourceReloadListener("shaolib_munitions/munitions")`
  → 完整路径是 `data/<namespace>/shaolib_munitions/munitions/<path>.json`，
  且 `<namespace>:<path>` 必须精确等于 MunitionPropertyType 的 id。
  写错路径不会报错，只会静默走 fallback —— 排查时看
  "Loaded N munition property set(s)" 的 N 值。

12.11 【版本对齐】
  本文档基于 shaolib_munitions 0.1.0 的反编译结果。
  build.gradle 用的是 curse 文件 id（shaolib 8728420 /
  shaolib-munitions 8728437），若与 0.1.0 不同版本，
  以下几处最可能变：
    - `NormalDualCannonProjectiles` 的方法签名
    - `MunitionPropertyComponents` 各 record 的字段顺序/数量
    - `MunitionsItems` 里的引信物品集合
  实施前先对着实际 jar `javap` 核对一遍。
