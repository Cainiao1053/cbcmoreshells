================================================================================
一、为什么它是对的
================================================================================

1) getBlock() 是「实例」状态，不是「类」状态 —— 这一点是它能成立的关键

   Registrate 的 .item(XxxBlockItem::new) 是每个方块各 new 一个 item 实例，
   构造时把自己的 Block 传进去。所以即使两个方块共用同一个 item 类，
   各自实例的 getBlock() 仍然返回各自的方块。

   这在本项目里是真实存在的情况：
     CBCMSBlocks.java:1120  EXTENDED_ANTIAIR_HE_SHELL 用的是
                            NormalAntiairHEShellBlockItem::new（不是 Extended 那个类）
   如果这个方法是按 item 类去查表，这里就会取错弹的属性；按 getBlock() 查则没问题。

2) 覆盖面完整，9 : 9 一一对应

   继承 FuzedDualCannonProjectileBlockItem 的 item 类（9 个）：
     NormalAPShotBlockItem            ExtendedAPShotBlockItem
     NormalHEShellBlockItem           NormalAntiairHEShellBlockItem
     NormalAPShellBlockItem           NormalAPBCShellBlockItem
     NormalSAPShellBlockItem          NormalIncendiaryHEShellBlockItem
     ExtendedAntiairHEShellBlockItem（未被注册使用，见「四」）

   CBCMSDualCannonMunitionRegistry.build() 里注册的方块（9 条）：
     NORMAL_AP_SHOT        EXTENDED_AP_SHOT
     NORMAL_HE_SHELL       NORMAL_ANTIAIR_HE_SHELL   EXTENDED_ANTIAIR_HE_SHELL
     NORMAL_AP_SHELL       NORMAL_APBC_SHELL
     NORMAL_SAP_SHELL      NORMAL_INCENDIARY_HE_SHELL

   注意惰性弹（AP Shot）也继承了 Fuzed 这个基类，所以「Fuzed」只是类名，
   实际覆盖了全部双联装炮弹，不用担心惰性弹漏掉。

3) 属性解析这一步永远不会失败

   properties(entry) → MunitionConfigManager.properties(propertyType)
   反编译 shaolib_munitions 确认它的行为是：

     Map.get(type.id())  →  为 null 就 return type.fallback()

   而且 properties 这个 static Map 在类静态初始化时就被 defaultProperties() 填好了。
   所以：
     - 数据包没加载 / 客户端还没收到服务端同步 → 拿到硬编码 fallback，不会 null、不会抛
     - 单机、多人、创造模式物品栏预览 都安全

4) 和现有写法一致

   9 个子类的 appendHoverText 里本来就在写
       CBCMSDualCannonMunitionRegistry.of(this.getBlock())
   新方法只是把这段上提到基类，思路没问题（但见 P3，应该顺手一起重构）。


================================================================================
二、问题
================================================================================

P1【真隐患，建议改】Objects.requireNonNull 会把「漏注册」变成客户端崩溃

   问题不在现在，在以后：只要有人新加一种弹，写了
       class NewShellBlockItem extends FuzedDualCannonProjectileBlockItem
   但忘了在 CBCMSDualCannonMunitionRegistry.build() 里 put 一条，
   of() 就返回 null，requireNonNull 立刻抛 NPE。

   这个方法的调用场景是 tooltip / GUI / 弹道表，都跑在客户端渲染线程上，
   NPE 直接把游戏崩掉，而不是少显示一行字。

   对比：现有的 CBCMSTooltip.appendInertDualCannonProjectileInfo 第一行就是
       if (entry == null || !Screen.hasShiftDown()) return;
   也就是说项目现有约定是「容忍 null」，新方法比现有代码更不设防。

   另外 requireNonNull 其实是多余的：即使去掉它，properties(entry) 里
   entry.propertyType() 一样会 NPE。它没有增加任何保护，只是换了个报错位置。

   → 改成返回 @Nullable，让调用方决定怎么降级。

P2【使用限制】不能在物品构造 / 注册阶段调用

   CBCMSDualCannonMunitionRegistry 的表是懒加载的，第一次 of() 会触发 build()，
   而 build() 里做了两件重的事：
     - CBCMSBlocks.NORMAL_AP_SHOT.get() —— Registrate BlockEntry 在注册完成前 .get() 会抛
     - 引用 CBCMSDualCannonProjectiles.XXX —— 触发它的静态初始化，
       进而 ShaolibProjectiles.register(...)

   所以 getProjectileProperties() 只能在「注册阶段结束之后」调用
   （tooltip、GUI、指令、弹道表都满足）。
   千万不要在 XxxBlockItem 的构造函数里调它去缓存结果。

P3【结构】加了基类方法，但 9 个子类还在各写各的

   现在基类有了 getProjectileProperties()，子类却还在重复
       CBCMSDualCannonMunitionRegistry.of(this.getBlock())
   建议基类同时暴露 getMunitionEntry()，9 个子类的 appendHoverText 改成调它。
   否则以后改查表方式要动 10 个地方。


================================================================================
三、语义说明（拿它做弹道表时必须知道）
================================================================================

这个方法返回的是「数据包里的基础属性」，不含每一发炮弹的运行时覆盖。
对弹道表来说这恰好是够用的，理由如下：

  · 每发覆盖只改 durability_mass
    MountedDualCannonContraption.spawnRound 用的是
        CBCMSDualCannonShotOverrides.encode(durabilityMassModifier, baseDurabilityMass)
    这个 2 参重载只写 ballistics.durability_mass 一个字段。
    （另有一个带 max_distance 的 3 参重载，当前双联装发射路径没有使用。）

  · 炮管不改初速
    spawnRound 里直接用 props.dualCannon().initialVelocity()，没有任何炮管系数。

  · 结论：drag / gravity / initialVelocity 三个弹道参数，
    getProjectileProperties() 拿到的值 = 实际飞行时用的值。
    可以直接喂给 CBCMSBallisticUtils 的 dualCannon* 系列方法。

  · 但这两个量不在返回值里，要另外取：
      寿命(tick)：entry.launchProfile().resolveLifetimeTicks(
                      props.dualCannon().baseLifetime(),
                      cannonMaterial.properties().addedLifetime(),
                      commandLifetimeModifier, equipmentLifetimeModifier)
      实际 durabilityMass：基础值 × 炮管 durabilityMassModifier × 指令 × 装备

    所以如果弹道表还要显示击穿能力，光有 getProjectileProperties() 不够，
    还得把 Entry 和炮管属性一起传进去 —— 这也是 P3 建议加 getMunitionEntry() 的原因。

五、建议的改法
================================================================================

FuzedDualCannonProjectileBlockItem 里改成：

    /** 这发炮弹在双联装注册表里的条目；方块没注册时返回 null。 */
    @Nullable
    public CBCMSDualCannonMunitionRegistry.Entry getMunitionEntry() {
        return CBCMSDualCannonMunitionRegistry.of(this.getBlock());
    }

    /**
     * 数据包里的基础弹药属性。不含每发的运行时覆盖，但覆盖只动 durability_mass，
     * 所以 drag / gravity / initialVelocity 可以直接用于弹道计算。
     * 只能在注册阶段结束后调用。
     */
    @Nullable
    public DualCannonMunitionProperties getProjectileProperties() {
        CBCMSDualCannonMunitionRegistry.Entry entry = getMunitionEntry();
        return entry == null ? null : CBCMSDualCannonMunitionRegistry.properties(entry);
    }

然后把 9 个子类 appendHoverText 里的
    CBCMSDualCannonMunitionRegistry.of(this.getBlock())
统一换成
    getMunitionEntry()
（CBCMSTooltip 的那几个 append 方法本来就接受 null，不用再加判断。）

如果调用方手里是 ItemStack 而不是 Item，注册表已经有现成的重载可以直接用，
不必绕到 item 类上：
    CBCMSDualCannonMunitionRegistry.of(stack)   // 内部就是 BlockItem.getBlock()
