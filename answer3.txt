我把 data/cbcmoreshells/shaolib_munitions/munitions/*.json 里的真实值全读了一遍，

  ✗ v1 说「maxDistance = 180 格是长射程的真正瓶颈」
    → 错。9 种弹的 json 里 max_distance 全是 5000.0，飞行路程根本不构成约束。

一、界面形态（v2 的核心改动）
================================================================================

v1 是「选弹 + 选材料 → 一张弹道表」，现在改成：

  第 1 屏  弹种选择（9 个）—— 只列种类，不解析属性
  第 2 屏  对比表 —— 一行一种材料，横向翻页看更多材料

第 2 屏的纵向结构（三块，自上而下）：

  ┌ 区块 A：不随材料变化的炮弹属性（单独一块，只画一次）
  ├ 区块 B：弹道骨架（与材料无关，列与下方弹道列一一对齐）
  └ 区块 C：材料对比表（一行一材料，左侧材料名 + 随材料变的属性 + 弹道列）

为什么要有区块 B：弹道骨架里的「仰角 / 落弹时间 / 存速」全都只由炮弹决定，
与材料无关（初速、阻力、重力都没有炮管系数）。如果塞进每一行会重复 N 遍。
区块 C 的弹道列里真正随材料变的只有【等效动量】和【能不能打到】两项。

  单管军用板岩 SINGLE_MIL_SLATE     1.12  +55t      宽单管钢 WIDE_SINGLE_STEEL          1.45  +85t
  宽单管板岩 WIDE_SINGLE_SLATE      1.58  +90t      宽单管军用板岩 WIDE_SINGLE_MIL      1.72 +110t
  大单管黄铜 LARGE_SINGLE_BRASS     1.78  +75t      宽单管强化钢 WIDE_SINGLE_TOUGH      1.92  +70t

  CAST_IRON(0.59/+5)  BRONZE(0.72/+20)  TOUGH_STEEL(1.20/+50)  ROSEQUARTZ_BRASS(0.84/+40)
  WIDE_ROSEQUARTZ_BRASS(1.25/+70)  NETHER_STEEL(1.00/+90)  WIDE_NETHER_STEEL(1.52/+140)

  （WIDE_NETHER_STEEL 的 +140t 是全表最长寿命、0.35 是全表最小散布，
    它被过滤掉的话，表里就看不到射程上限最高的那个选项了。）

建议做法：过滤器做成两段式，默认开「补漏」

  DualCannonMaterialFilter
    SINGLE_ONLY        严格 isSingleBarrel，14 个
    SINGLE_PLUS_GAPS   isSingleBarrel 的全要 + 那些「没有任何单管孪生体」的双管材料，

    ALL                35 个都要，调试用

  这三项决定了弹道相关的一切；reloadTimeModifier 单/双管会差一点点，
  按你的要求以单管的为准。
  你以后把缺的单管补齐，SINGLE_PLUS_GAPS 的补漏名单会自动收缩到空，代码不用改。

三、属性分层：随材料变 vs 不随材料变
================================================================================

这是你的需求 4，做成【类型级别】的区分，而不是一个布尔标记——
这样「不随材料变的属性」在编译期就不可能误读到材料字段。

3.1 两个上下文

  /** 只有炮弹，没有炮管。区块 A 和区块 B 用它。 */
  public record DualCannonShellContext(
      CBCMSDualCannonMunitionRegistry.Entry entry,
      DualCannonMunitionProperties          shell
  ) {
      double muzzleVelocity(); double drag(); double gravity();
      double baseMass(); double maxMomentum(); double deflectionAngleDeg();
  }

  /** 炮弹 + 一种炮管材料。区块 C 的每一行用它。 */
  public record DualCannonLoadout(
      DualCannonShellContext shell,
      DualCannonMaterial     material,
      DualCannonMaterialProperties barrel,
      int    barrelBlocks,          // 身管格数，只影响散布，UI 上给个输入框
      float  commandModifier,       // 预留，默认 1
      float  equipmentModifier      // 预留，默认 1
  ) {
      double durabilityModifier();  // barrel.durabilityMassModifier() * command * equipment
      double effectiveMass();       // shell.baseMass() * durabilityModifier()
      int    lifetimeTicks();       // (shell.baseLifetime + barrel.addedLifetime) * mods
      double explosionPower();      // 基础爆炸 * DualCannonModifiers.explosionPower(kind, mod)
      double reloadCoefficient();   // 弹 reloadTimeCoefficient * barrel.reloadTimeModifier()
      double spread();
  }

3.2 两个 StatSpec 类型（泛型一套即可）

  public record StatSpec<C>(
      String key,                       // 翻译键，同时用作列头
      ToDoubleFunction<C> value,        // 返回 NaN = 本弹种不适用，UI 跳过
      StatFormat format,                // PLAIN2 / PERCENT / M_PER_SEC / SECONDS / DEGREES / TICKS
      int priority                      // 列不够时按 priority 从低往高折进 tooltip
  ) {}

  public interface StatSink<C> {
      void add(StatSpec<C> spec);
      void addIf(boolean cond, StatSpec<C> spec);
  }

3.3 物品上的两个收集口（需求 4 / 5 的落点）

  在 FuzedDualCannonProjectileBlockItem 上：

  /** 区块 A：不随材料变化的属性。 */
  public void collectShellStats(StatSink<DualCannonShellContext> sink) {
      sink.add(DualCannonStats.MUZZLE_VELOCITY);   // 初速 m/s
      sink.add(DualCannonStats.DRAG);
      sink.add(DualCannonStats.GRAVITY);
      sink.add(DualCannonStats.BASE_MASS);         // 基础弹头质量（未乘材料）
      sink.add(DualCannonStats.DEFLECTION_ANGLE);  // 跳弹角，acos(deflection)
      sink.add(DualCannonStats.MAX_MOMENTUM);      // 动量封顶
      sink.add(DualCannonStats.SMASH_TOUGHNESS);
      sink.add(DualCannonStats.MAX_RANGE);         // 弹道最大射程 + 最优仰角
  }

  /** 区块 C 的前几列：随材料变化的属性。这里只声明列，值在渲染每一行时求。 */
  public void collectMaterialStats(StatSink<DualCannonLoadout> sink) {
      sink.add(DualCannonStats.MASS);        // priority 100
      sink.add(DualCannonStats.LIFETIME);    // priority 100  ← 决定可达射程，必须留
      sink.add(DualCannonStats.RELOAD);      // priority 80
      sink.add(DualCannonStats.SPREAD);      // priority 60
  }

  子类按弹种加：
    HE / APHE / APBC / SAP / 防空 / 燃烧
        collectMaterialStats 里 super(...) 后 add(EXPLOSION_POWER)     priority 90
    防空 HE
        再 add(AA_ALTITUDE_BONUS)（每 80 格 +1，封顶 ×3）  —— 这个不随材料变，
        所以其实该放 collectShellStats，注意别放错块
    燃烧 HE
        再 add(FIRE_CHANCE) / add(FIRE_RANGE)              priority 85
    AP Shot（惰性）
        不加爆炸列（Kind.AP_SHOT 的 explosionPowerMultiplier 恒为 0）

  所有 StatSpec 常量集中在 DualCannonStats 一个文件里。
  加一个新属性 = 加一个常量 + 在某个 Item 里 add 一行，其他文件一律不动。

3.4 弹道区显示什么，也按弹种可配

  因为高爆/防空/燃烧弹的等效动量恒等于 0.2~2.6（质量 0.1、封顶 10），显示它是浪费列。
  所以再加一个口：

  /** 弹道列显示的量。默认「等效动量」，切换按钮在这个列表里轮换。 */
  public List<BallisticColumnMode> ballisticModes() {
      return List.of(BallisticColumnMode.MOMENTUM, BallisticColumnMode.FLIGHT_TIME);
  }
  高爆类覆写成 List.of(FLIGHT_TIME, IMPACT_SPEED)，把动量换掉。

  enum BallisticColumnMode { MOMENTUM, FLIGHT_TIME, IMPACT_SPEED, ELEVATION }

  注意：FLIGHT_TIME / IMPACT_SPEED / ELEVATION 都【与材料无关】，
  切到这些模式时每一行的数值完全相同。此时建议 UI 把区块 C 的弹道列折叠掉，
  只保留区块 B 里那一行——否则就是把同一行数字抄 14 遍。
  （如果你更想要「按钮一按整块切换」的直观感，也可以照抄 14 遍，功能上没问题，
    但我建议前者。这一条留给你定。）

3.5 动量公式扩展点（需求 7，沿用 v1）

  public DualCannonMomentumModel momentumModel() { return DualCannonMomentumModel.CAPPED; }

  DualCannonMomentumModel.CAPPED = (l, v) ->
      DualCannonPenetrationModel.getCappedMomentum(l.shell().shell(), v, l.effectiveMass());

四、列预算（需求 5）
================================================================================

  TOTAL_COLUMNS      可配，默认 15（UI 上给个 12/15/18 的下拉）
  1                  材料名，固定占 1 列
  M                  collectMaterialStats 声明的列数（按弹种不同，4 ~ 7）
  B = TOTAL - 1 - M  弹道列数

  实例（APHE，M=5：质量/寿命/爆炸/装填/散布）：TOTAL=15 → B=9

  保底规则
    if (B < MIN_BALLISTIC_COLUMNS /* 建议 4 */) {
        按 priority 从低到高，把材料属性列折进「悬停材料名显示全部属性」的 tooltip，
        直到 B >= 4；仍然不够就强制把 TOTAL 抬到 1 + M + 4 并在界面上提示。
    }
  这就是 StatSpec.priority 存在的理由：列不够时机器知道先砍哪个。

  弹道列的距离取法
    等分该弹的弹道最大射程：d_i = maxRange * i / B  (i = 1..B)
    列头写实际距离（如 57.2 / 114.4 / …），全表共用一套距离，
    所以区块 B 和区块 C 的列能严格对齐。
    （备选：固定绝对距离 50/100/150…，好处是跨弹种可比，坏处是短射程弹会有空列。
      建议做成一个开关，默认等分。）

五、惰性计算与缓存（需求 3）
================================================================================

  开界面
    只读 CBCMSDualCannonMunitionRegistry.all() 拿 9 条 Entry（不解析属性），画 9 个格子。

  选中某弹（一次）
    1) properties = MunitionConfigManager 解析出来的该弹属性
    2) shellCtx = new DualCannonShellContext(entry, properties)
    3) 区块 A：item.collectShellStats(...) 求值
    4) 算 M → 算 B
    5) 区块 B 骨架：CBCMSBallisticUtils.dualCannonMaxRange + dualCannonRangeTable(..., B, lowArc)
       只算 1 次，得到 B 个 BallisticPoint（距离/仰角/落弹时间/存速/所需tick）

  材料列表（一次）
    DualCannonMaterial.all() → 按过滤器筛 → 按 durabilityMassModifier 升序 → 灌进 Paginator

  渲染每一页（只算当前页那 ~10 行）
    对页内每个 material：
      loadout = new DualCannonLoadout(shellCtx, material, material.properties(), barrelBlocks, 1, 1)
      材料属性列 = collectMaterialStats 的每个 StatSpec.value(loadout)
      弹道列     = 对每个 BallisticPoint：
                     momentum   = item.momentumModel().momentum(loadout, point.impactSpeed())
                     reachable  = point.ticks() <= loadout.lifetimeTicks()
    结果放进 Map<DualCannonMaterial, MaterialRow>，换弹/换过滤器/关界面时清空。

  代价：每行只有几十次乘法 + 一次 momentum 调用，一页 10 行完全无感。
  骨架那一步（B 次射程反解，每次 Lambert + Newton）也只有毫秒级，且每弹只做一次。

  另外：不要在开界面时做全量预热。你已经明确要「选到谁算谁的」，
  而且 /reload 改数据包后必须立刻反映出来，所以整个缓存的生命周期 = 一次界面会话。

八、前置修复清单（做 UI 之前必须先处理）
================================================================================

P1【必修】getProjectileProperties() 的 Objects.requireNonNull 去掉，改 @Nullable
     UI 要遍历全部 9 种弹，任何一个漏注册都会整屏崩客户端。

     CANNON_MATERIALS 是 private static HashMap，没有任何公开访问器。
     加 public static Collection<DualCannonMaterial> all()，
     并把 HashMap 换成 LinkedHashMap —— 否则表格里材料顺序每次启动都不一样。

P3【必修】倍率公式锁在 DualCannonBehavior 的实例方法里

        static double incendiaryRange(double durabilityModifier)
        static double antiairAltitude(double climbBlocks)
     DualCannonBehavior 改成调它。纯搬家，行为不变。

P4【必修，直接影响本表】寿命有两个来源，而且现在的 tooltip 是错的
     实际飞行用的是：
        launchProfile.resolveLifetimeTicks(props.dualCannon().baseLifetime(), 材料addedLifetime, …)
        而 9 个 json 里都没有 "baseLifetime" 键 → 全部走 fallback 20 tick
     tooltip 显示的却是：
        entry.launchProfile().baseLifetimeTicks()   （AP弹 40 / AP穿甲 30 / 防空 0 …）
     两者完全对不上（例：单管钢 APHE 实际 70t=3.5s，tooltip 显示 30t=1.5s；
     防空弹 profile 写 0，实际是 20+材料）。
     必须先定哪个是权威：
       方案甲  json 里补上 baseLifetime，profile 里那个字段删掉，tooltip 改读 properties
       方案乙  resolveLifetimeTicks 改成用 profile 的值，properties 里那个删掉
     没定之前，表格的「寿命」列和「打不到」判定都没法确定口径。

P5【必修】json 键命名不一致，容易继续踩
     DualCannonLaunchProperties.fromJson 里 9 个字段是 snake_case，
     唯独 baseRecoil / baseLifetime 两个是 camelCase；
     DualCannonImpactProperties.fromJson 里也唯独 minDeflection 是 camelCase。
     数据包作者按 snake_case 写 base_lifetime / min_deflection 会静默失效。
     建议两种都接受（先读 snake_case，回退 camelCase），像 initial_velocity/initial_vel 那样。

P6【必修】主/副炮散布公式不等价
     MountedDualCannonContraption:539-541  max(spread - sub*L, 弹minSpread + 材料minSpread)
     MountedDualCannonContraption:553-555  材料minSpread + max(spread - sub*L, 材料minSpread)
     看着是复制粘贴改漏。表格要显示散布，得先定用哪个。

P7【必修，否则扩展点会踩空】ExtendedAntiairHEShellBlockItem 是死代码
     CBCMSBlocks.java:1120 给 EXTENDED_ANTIAIR_HE_SHELL 传的是
     .item(NormalAntiairHEShellBlockItem::new)，那个 Extended 类从来没被注册使用。
     本方案要求把 collectShellStats / collectMaterialStats / ballisticModes /
     momentumModel 写在物品里，写进 Extended 那个类会完全不生效且极难查。

P8【必修】8 个材料缺 lang 键，材料名列会显示成翻译键原文
     缺：hamlet_steel, podia_zinc, starlight_ingot, large_brass, large_steel,
         large_single_brass, large_single_steel, large_single_slate_alloy
     其中 large_single_* 三个属于 isSingleBarrel 集合，默认过滤器下就会露出来。
     键格式沿用现有的 block.cbcmoreshells.material.<path>。

P9【建议】DualCannonPenetrationModel.resolve() 内联了和 getCappedMomentum 一样的算式
     resolve() 第 76-80 行 和 getCappedMomentum 第 104-108 行是同一段公式抄两遍。
     让 resolve() 调 getCappedMomentum，否则以后改公式会出现
     「表上写能穿、实战打不穿」。
     进阶：把 momentumModel 也存一份到 Entry 上，让 resolve() 取到同一个实现，
     这样需求 7 在实战侧也生效，而不只是表格好看。
